# План разработки

## О проекте

Учебный проект для отработки gRPC (контракт-first) и Avalonia UI на предметной области учёта сотрудников: отделы, должности, сотрудники, задачи.

## Стек

- Сервер: C# / .NET, gRPC (Grpc.AspNetCore), PostgreSQL, Npgsql
- Контракты: отдельная библиотека с .proto-файлами, референсится и сервером, и клиентом (один источник правды, без ручной синхронизации)
- Клиент: Avalonia UI, ReactiveUI (MVVM), Grpc.Net.Client
- Дизайн: Figma (макеты + UI kit), темы клиента

## Структура репозитория

Сейчас в решении нет проектов — это сознательно, реализация начинается только после дизайна. На этапе "Контракты + сервер" появятся:

- `Employees.Contracts/` — .proto контракты
- `Employees.Server/` — gRPC-сервер + доступ к БД
- `Employees.Client/` — Avalonia-клиент

## Модель данных

- **Должность**: id, name, salary (оклад)
- **Отдел**: id, name
- **Сотрудник**: id, f_name, l_name, m_name, date_birth, gender, id_отдела (FK), id_должности (FK), rate (ставка занятости, например 1.0 / 0.5 / 0.25), id_задачи (FK, nullable — текущая задача)
- **Задача**: id, name, date_start, date_end

ЗП сотрудника = `Должность.salary × Сотрудник.rate`, не хранится отдельным полем — считается на лету.

Удаление отдела, должности или задачи, на которые ссылается хотя бы один сотрудник, запрещено (restrict), а не каскадное удаление.

## Функционал

- Должности: добавить / изменить / удалить
- Отделы: добавить / изменить / удалить
- Задачи: добавить / изменить / удалить
- Сотрудники: добавить / изменить / удалить; при создании — выбор отдела и должности, проверка возраста 18+ (при выставлении ставки сервер принимает разделитель - запятая, а вернет разделитель - точка)
- На карточке сотрудника — текущий статус: "свободен" либо название задачи + срок окончания

## UX

Главное окно — вертикальный `TabControl` слева с 4 вкладками: Должности, Отделы, Сотрудники, Задачи.

Каждая вкладка — самостоятельный `UserControl`, полностью закрывающий CRUD по своей сущности: список, форма добавления, удаление, и отдельное модальное окно редактирования.

## Адресация к серверу

IP и порт сервера не зашиваются в код. Клиент читает конфиг (`client.config.json`, не коммитится) рядом с исполняемым файлом при старте через `IConfiguration`. После публикации клиента (`dotnet publish`) пользователь открывает этот файл и прописывает адрес своего сервера — пересборка не нужна. Пошаговая инструкция появится в README, когда будет что публиковать.

## Безопасность (минимальный уровень для публичного сервера)

- TLS на gRPC-канале — без него трафик в открытом интернете читается кем угодно
- Простая аутентификация (токен или логин/пароль через interceptor) — без неё сервер открыт всем, кто узнал IP
- Вся валидация (18+, обязательные поля, ссылочная целостность) дублируется на сервере — клиенту не доверяем
- Секреты (строка подключения к БД) — только через переменные окружения/appsettings на сервере, не в репозитории

## Этапы разработки (waterfall)

1. **Дизайн** — ERD, .proto контракты, Figma-макеты + UI kit *(текущий этап)*
2. **Контракты + сервер** — .proto, доступ к БД, реализация gRPC-сервисов, серверная валидация
3. **Клиент-каркас** — Avalonia + MVVM, вертикальный TabControl, DI, подключение по gRPC через конфиг
4. **Фичи** — CRUD-формы на всех 4 вкладках, модальные окна редактирования, отображение "свободен / задача"
5. **Защита** — TLS, авторизация, серверная валидация, логирование ошибок без падений и утечек данных
6. **Деплой** — сервер на VPS (systemd-сервис), публикация клиента, конфиг-файл рядом с exe, инструкция в README
7. **v2 (бэклог)** — роли/логин, история назначений на задачи (many-to-many вместо одной FK), поиск/пагинация, темы, тесты

Каждый этап закрывается полностью, прежде чем начинается следующий.
